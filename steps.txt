# Chronos — Phase 3: Distribution & Durability (Build Workflow)

Build in this order — each step builds on the last.

## Step 1: Exactly-once execution (idempotency)

The problem: a worker runs "charge customer", charges them, then crashes BEFORE
reporting success. The queue redelivers the task -> another worker runs it again
-> customer charged twice. Retries must not duplicate side effects.

What to build:
- Every step attempt gets a deterministic key: runId + stepId (NOT UUID-per-retry;
  same step = same key).
- Flow per execution:
  1. Worker writes StepStarted(attempt=1) to the event log BEFORE running anything.
  2. Runs the Java Step handler.
  3. Writes StepCompleted.
- On any redelivery, worker checks the event log first: if StepCompleted already
  exists for that key -> skip, ack the message, done.
- Hard case: crashed DURING the side effect (after charging, before completing).
  Two-phase solution:
    - write an "intent" row
    - do the effect
    - write "done"
  On retry, if intent exists without "done": query the downstream system (did the
  charge go through?) or make the effect itself accept the idempotency key
  (most payment APIs support this). Handle this path in tests.

## Step 2: Worker pool + Redis reliable queue

The problem: scheduler currently runs steps as threads in its own process.
Doesn't scale and isn't crash-tolerant. Need separate worker processes pulling
work off a queue that never silently drops a task.

What to build:
- Split into two Spring Boot apps (or profiles): `scheduler` and `worker`.
- Scheduler finds a ready step -> pushes a task message (JSON: runId, stepId,
  attempt) into Redis.
- Workers loop: take message -> execute step -> write result event -> ack.
- The "reliable" part: naive LPUSH/BRPOP loses messages if a worker dies holding
  one. Worker moves the message to a "processing" entry with a claim timestamp;
  a janitor thread re-enqueues anything claimed longer than X seconds ago
  (visibility timeout). Prefer Redis Streams with consumer groups
  (XREADGROUP + XAUTOCLAIM) over lists — mostly free reliability.

## Step 3: Leader election (Postgres advisory locks)

The problem: two scheduler instances both deciding "step 3 is ready" dispatch it
twice. Need exactly one active scheduler; if it dies, another must take over
within seconds — automatically.

What to build:
- Each scheduler instance, on startup and on a timer, runs:
    SELECT pg_try_advisory_lock(12345);
  Winner becomes leader.
- Leader loop: check lock still held -> find ready steps -> dispatch ->
  sleep ~100-500ms.
- Failover is free: advisory locks are session-scoped, so when the leader's DB
  connection dies, Postgres releases the lock and another instance's next try
  succeeds.
- Split-brain guard: a paused/zombie leader can wake up not knowing it lost the
  lock. Before EVERY dispatch batch, re-verify the lock (pg_advisory_lock held
  check on the same connection), or include a leader epoch/fencing token in
  dispatched messages and have workers reject stale epochs.

## Step 4: Durable timers service

The problem: "wait 24 hours then send follow-up". Can't Thread.sleep — a deploy
or crash loses it. Timers must survive full cluster restarts.

What to build:
- Workflow hits a wait step: write TimerScheduled(runId, firesAt, timerId) event,
  mark the workflow paused, stop executing it.
- Separate lightweight `timer` service polls Postgres every ~1s:
    SELECT ... WHERE fires_at <= now() AND NOT fired
      FOR UPDATE SKIP LOCKED;
  (skip-locked prevents double-firing with multiple timer instances later)
- For each due timer: write TimerFired event -> scheduler's normal replay logic
  sees the wait step satisfied -> resumes the workflow.
- Crash-safety is automatic because state lives in the event log — restart
  everything, poller resumes, nothing lost.

## Step 5: Child workflows

The problem: parent workflow needs "run sub-process and wait for its result" —
e.g. "onboard tenant" spawns "provision resources" and "create billing account"
as separate runs, continues when both finish.

What to build:
- New step type StartChildWorkflow: creates a fresh run (own event log) and
  records ChildStarted(parentRunId, childRunId) on the parent's log.
- Parent just waits like a human-in-the-loop step.
- When child run completes, scheduler writes ChildCompleted(childRunId, result)
  to the parent's log -> parent wakes up, result available to subsequent steps.

## How it all connects at runtime

Scheduler (leader) replays event logs -> computes ready steps -> enqueues to
Redis -> workers pull, execute with idempotency keys, report events back ->
timers and signals inject events from outside.

One rule: THE EVENT LOG IS THE ONLY SOURCE OF TRUTH. All components just read
it and append to it.

## Checkpoint before starting

Confirm a crash BETWEEN two steps replays the event log and resumes exactly at
the next step on a single node. If that's solid, distribution is mostly about
delivery reliability; if not, scale-out multiplies the bugs.

Tip: write mini chaos tests as you go in steps 2-4 (kill -9 a worker mid-step,
kill the leader mid-dispatch) rather than saving them all for phase 4.
